Design Documentation

ACG Monopoly

A real-time multiplayer implementation of Monopoly for a class-sized group, built on an authoritative server so that game state cannot be altered by a modified client.

Language TypeScript (strict) Client React 18 + Vite Server Colyseus 0.18 Deployment Fly.io, single machine

1System architecture

The system is a single Node.js process that serves both the compiled React client and the game server. Clients connect over a WebSocket and are never trusted: they send intents such as "roll" or "buy", and the server decides what actually happens.

This division is the central design decision. Every rule — whose turn it is, whether a purchase is affordable, whether a colour group is complete — is evaluated on the server. A player who edits values in their browser's developer tools changes only their own screen, because the next state broadcast overwrites it.

Why one process

Colyseus rooms live in memory. Spreading them across several processes requires Redis for shared presence and matchmaking, or two players entering the same room code would land on different machines and never see each other. At a class-sized scale of roughly 20–30 players, one machine removes that entire category of infrastructure, so the deployment declares a single Fly machine with min_machines_running = 0.

4Message protocol

This is the complete set of messages a client may send. Anything else is ignored. Every handler re-checks the sender's right to act before touching state, so validation does not depend on the client having disabled a button.

rejectTrade{ tradeId }Sender is the recipient

A rejected message returns an error message naming the reason, which the client shows as a transient notice. The 21 rejection paths are what a modified client meets when it tries anything illegal.

Room access

Rooms are addressed by a five-character code drawn from an alphabet that excludes I, O, 0 and 1, so a code read off a screen cannot be mistyped through ambiguity. Creating uses create() and joining uses join(), deliberately not joinOrCreate(): a mistyped code must be an error, rather than silently producing a second empty room the rest of the group can never find. An optional CLASS_PASSCODE environment variable adds a shared passcode, and the join screen queries GET /config so the passcode field only appears when one is actually required.

5Turn state machine

A turn is a finite state machine with five states. Each message handler declares which states it accepts, and requireTurn() rejects anything arriving in the wrong one — so an out-of-order message cannot corrupt the game, it is simply refused.

StateMeaningAccepts
lobbyWaiting for players; nobody has startedstart (host only)
rollingCurrent player must roll, or pay to leave jailroll, payFine
decidingLanded on an unowned property they can affordbuy, decline
actingMove resolved; may trade houses or end the turnendTurn, build, sell, mortgage, unmortgage
endedOne player remains; result written to disknothing

Property management messages are accepted in any state, not only on the sender's own turn, because a player in debt must be able to raise cash while someone else is rolling.

6Data structures

Each structure is implemented from scratch in src/structures/ and chosen because the problem has that shape, not to demonstrate the structure. The justification for each is given below.

The board is a circular linked list

A Monopoly board is physically a ring: each square leads to the next, and the last leads back to the first. Modelling it as an array with % 40 arithmetic works, but the awkward cases live in the wrap — landing exactly on GO, or a card sending a player backwards past it. As a ring, "did I pass GO?" becomes "was GO one of the squares I stepped through", which is true by construction.

Every structure and its justification

StructureUsed forWhy this one
CircularLinkedListThe board The domain is literally a ring; passing GO falls out of the traversal
LinkedListHash table chains Collision chains only ever grow at the head and are scanned linearly — O(1) insert with no resizing
CircularQueueTurn order Ending a turn is exactly "dequeue the front and enqueue it at the back"; no wrapping index to get wrong
QueueChance / Community Chest draw piles The real rule returns a used card to the bottom of the pile — first in, first out
StackChance / Community Chest discard piles The most recent card sits on top, and the whole pile is turned over — popped one at a time — to refill the draw queue when it empties
HashTablePlayer lookup by session ID Every incoming message needs this lookup. O(1) average versus O(n) for a scan. Uses djb2 hashing with separate chaining and resizes above a 0.75 load factor
BinarySearchTreeProperty lookup for the trade screen O(log n) search by name, and a prefix search built on the in-order traversal returns matches already in alphabetical order — which a hash table cannot do. Reached live through the searchProperty message

A design tension worth stating

Colyseus's MapSchema is what actually travels over the network, so the hash table does not replace it. The split is deliberate: the schema is the wire format, and the structures are the engine. Game logic reads through playerIndex so that the rules do not depend on the transport library's data types, and the schema exists purely to be synchronised.

7Algorithm analysis

Complexities below are in terms of n, the number of items held by that structure. The practical sizes in this game are small — at most 6 players, 28 properties, 16 cards per deck — which is what makes the O(n²) sorts a reasonable choice rather than a compromise.

OperationBestAverageWorstNotes
LinkedList.addFirstO(1)O(1)O(1)No shifting, unlike an array insert
LinkedList.find / removeO(1)O(n)O(n)Must follow pointers from the head

Queue.enqueueO(1)O(1)O(1)
Queue.dequeueO(1)O(1)O(n)Amortised O(1): a head index moves instead of shifting, and the dead prefix is reclaimed occasionally

HashTable.resizeO(n)O(n)O(n)Rare; every key must be re-hashed because the index depends on capacity
BST.insert / searchO(log n)O(log n)O(n)Worst case is sorted insertion, which degenerates into a linked list
BST.inOrderO(n)O(n)O(n)Every node is visited exactly once
bubbleSortO(n)O(n²)O(n²)Best case needs the early exit when a pass makes no swaps
insertionSortO(n)O(n²)O(n²)Best case is nearly-sorted input — exactly the leaderboard's case
binarySearchO(1)O(log n)O(log n)Requires the array to be sorted; O(1) memory iteratively, O(log n) stack frames recursively

Choosing between the two sorts

Both are quadratic in the average case, so the choice is made on the shape of the data rather than the asymptotic bound.

  • Bubble sort ranks the end-of-game standings. There are at most six entries and it runs once per game, immediately before a file write that costs far more than the sort. Simplicity is worth more than speed here, and the early-exit pass makes it O(n) when the order has not changed.
  • Insertion sort maintains the leaderboard. The array is already sorted and one new player is out of place, which is insertion sort's best case: the inner loop only runs until the gap is found. Re-running a general-purpose sort over an almost-sorted array would do far more work for the same result.

A test asserts this rather than assuming it: insertionSort is measured against bubbleSort on nearly-sorted input and must use strictly fewer comparisons.

Recursion

Recursion is used where the data is itself recursively defined — a tree is a key plus a left tree and a right tree — and avoided where a loop is clearer.

Recursive functionBase caseMaximum depth
BST.insertIntoAn empty subtree becomes the new leafTree height (7 for 28 properties)
BST.searchFromEmpty subtree, or an exact key matchTree height
BST.traverseInOrderA null node returns immediatelyTree height
BST.heightOfA null node has height 0Tree height
moveRecursiveZero steps remaining12 (the largest two-dice roll)
binarySearchRecursiveEmpty range, or a match at the midpointlog₂ n

Every depth above is bounded and small, so stack overflow is not a practical risk. moveRecursive and binarySearchRecursive duplicate iterative versions on purpose, and tests assert the two forms agree — the recursive walk is checked against the iterative one for all 40 starting squares across four step counts.

Which recursion runs during a game

The BST's recursive insertInto runs at startup, indexing all 28 properties. Its recursive searchFrom and traverseInOrder run whenever a player types in the trade screen's search box. moveRecursive and binarySearchRecursive are deliberate duplicates of the iterative versions, kept for comparison and covered by tests that assert the two forms agree; the live paths use the iterative move() and binarySearch().

Error handling

File access is the most likely thing to fail at runtime, so each failure mode has a defined behaviour rather than being allowed to crash the server:

ConditionBehaviourReasoning
File does not existStart with an empty leaderboardThis is the normal first run, not an error
File contains invalid JSONLog the problem, start empty, carry onLosing a leaderboard is far better than refusing to start the server
Directory missing on writeCreated with recursive: trueRemoves a first-run failure entirely
Write fails (permissions, disk)Log the error; the game continuesAn unsaved result must not interrupt play
File hand-edited out of orderRe-sorted on load with insertion sortBinary search is only correct on sorted data, so the invariant is restored rather than assumed

Limitation in production

The data directory lives inside the container. With min_machines_running = 0 the Fly machine stops when nobody is playing, and its filesystem goes with it. Persisting a deployed leaderboard requires a Fly volume mounted at /app/data. Locally, and on a machine that stays running, the files persist as expected.

10Defects found and fixed

Both defects below were found by the test suite, not by playing. Both had been present and unnoticed through earlier manual testing, which is the argument for writing the tests at all.

Defect 1 — a two-player game never ended

Symptom. A bot-driven game ran 60,000 actions with both players marked bankrupt and no winner declared.

Cause. When a player went bankrupt on their own turn — the normal case, since you go bust paying rent — bankrupt() called nextTurn(), which found the one surviving player, set the phase back to rolling and returned. checkForWinner() was only reached if nextTurn() found nobody to play, so the survivor played on alone forever.

Fix. Advance the turn if needed, then always check for a winner. checkForWinner() now returns early when the game has already ended, and handles the all-bankrupt case rather than hanging.

Defect 2 — lifting a mortgage overcharged by £1

Symptom. A test expected Mayfair's unmortgage cost to be £220 and got £221.

Cause. The cost was calculated as Math.ceil(value * 1.1). The decimal 1.1 has no exact binary representation, so 200 * 1.1 evaluates to 220.00000000000003, and rounding that up adds a pound.

Fix. Integer arithmetic — Math.ceil(value * 11 / 10) — which gives exactly 220. A general lesson for any money calculation: never scale currency by a decimal fraction.

Known limitations

  • No auctions. A declined property stays with the bank rather than going to auction.
  • No house or hotel supply limit. The real game has 32 houses and 12 hotels; here they are unlimited.
  • Free Parking collects nothing, which matches the printed rules rather than the common house rule.
  • Games are not resumable. A server restart loses any game in progress; only completed results persist.
